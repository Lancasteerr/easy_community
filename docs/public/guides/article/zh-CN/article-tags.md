# 文章标签：JSON 存储与本地目录搜索

## 业务与接口

标签只允许管理员新增，名称去首尾空白后为 1～32 个 Unicode 码点，沿用区分大小写的唯一性规则。不提供改名、禁用、删除、合并或使用次数统计。文章允许 0～5 个标签，保存时先限制原始输入数量，再去重、按数值排序，并覆盖整个集合。

| 接口 | 权限与行为 |
|---|---|
| `GET /api/tags?q=spring&limit=10` | 登录后搜索，返回 `[{"tagId":"1","name":"Spring Boot"}]` |
| `POST /api/admin/tags` | ADMIN + CSRF；请求 `{"name":"Java"}`，201 返回 TagView，重名为 409 TAG_EXISTS |
| `POST /api/articles` 的 `tagIds` | 使用既有字符串 ID 数组；空数组清空标签，不接收名称或自动创建标签 |

`q` 缺省或规范化后为空返回 `[]`，不再返回整个目录。原始关键词最多 128 个 Unicode 码点，规范化后最多 32 个；`limit` 默认 10，范围 1～20，非法参数返回 400。普通搜索不存在的名称直接返回 `[]`，不会检查 SQL 版本。

目录加载时预计算 NFKC、去首尾空白、小写（Locale.ROOT）的搜索字段，查询词使用相同规则。前缀匹配优先，其后补包含匹配；同级按搜索字段和数值 ID 稳定排序。搜索规范化不改变名称判重规则，`Java` 与 `java` 仍可作为不同标签存在。

文章详情、编辑、列表继续返回 `tags: [{tagId,name}]`，不改变 HTTP 标签字段或 ID 类型。本轮不修改前端。

## 存储及索引

V8 新增单行 `tag_dictionary_meta(id=1,version)`，初始版本为 1。所有标签新增和版本递增必须在同一事务提交，回滚或重名不能增版。不得绕过版本直接维护目录，版本不能用 MAX(id) 或时间戳代替。

V9 将旧关系回填到 `article.tag_ids JSON NOT NULL`，使用数字数组，例如 `[1,3,5]`；没有标签为 `[]`。窗口聚合固定 ID 顺序，包含隐藏文章。CHECK 保证数组类型及最多五项；旧关系的主键和外键保证回填来源去重且引用存在。历史超限导致迁移失败，不截断。

运行中的文章读写和索引维护不再访问 `article_tag`。首次发布仍保留旧表用于核对，物理删除留到验证后的独立发布。JSON 不提供逐元素外键，所有线上保存都必须通过 ArticleService 的统一标签校验。

标签 JSON、文章元数据版本及 Outbox 与正文修改同事务提交。ES 继续使用原有 `tagIds` keyword 数组、条件更新和墓碑；单次批量文章元数据查询就能获得标签，导入/回放不读取目录缓存，也不再查询关系表。ES 候选的标签条件使用当前文章投影再核对一次，不额外查询 SQL；新增文章或新标签的发现仍接受索引同步延迟。

## 本地快照及校验

每个 Web 实例保留一份不可变 `TagSnapshot`，其中包含版本、预计算搜索列表和按 ID 查找的映射。通过 AtomicReference 原子替换，只安装更高版本，不落盘、不写 Redis、不维护关键词结果缓存。

完整加载在独立只读 RR 事务中先读版本、再读全部标签，返回后构建快照，防止版本与目录内容不匹配。轻量版本查询使用独立 RC 事务，当前应用只有主库数据源，不继承文章事务快照。

文章事务开始前，对整个目标集合执行以下校验：

1. 空集合直接通过；本地目录全部命中直接通过，两者均为零标签 SQL。
2. 缺少任意 ID 时只查询一次主库版本；如果低于操作开始时的本地版本，返回 503 DEPENDENCY_UNAVAILABLE。
3. 查询返回后重读本地引用。其他线程已补齐则通过；当前快照版本不低于 SQL 版本时，直接判断集合是否完整。
4. 本地版本落后才同步一次完整快照，必须达到已观察到的 SQL 版本，再检查全部 ID。
5. 完整目录仍缺 ID，保存返回 400 INVALID_ARTICLE；版本查询、同步、等待失败返回 503，不误判为非法。

不再执行 COUNT/IN 标签存在性查询，不逐个回源，也不循环追赶持续新增版本。标签只新增、不失效，因此验证后到文章提交之间无需再次确认或锁标签行。将来引入禁用或删除时必须重新设计该前提。

文章 SQL 读取和 Redis 投影只携带 ID，名称在文章事务及缓存锁释放后通过本地目录批量装配。一页使用同一快照。对于文章中已经持久化但本实例尚未加载的 ID，使用同样的版本检查和同步流程；完整目录仍缺失时视为数据错误，记录告警并返回 503，不漏标签、不写文章不存在的负缓存。

## 刷新与故障

- Web 实例启动尝试加载完整目录；未初始化返回 503，与已加载的空目录区分。加载失败不影响其他独立模块。
- `TAG_REFRESH_DELAY` 默认 `60s`，每实例按 fixed-delay 检查版本，首次定时检查随机错峰 0～60 秒；版本未变只执行一次版本 SQL。
- 管理员新增事务代理返回后尽力刷新本实例，失败不覆盖已提交的新增响应；其他实例通过定时检查更新。
- 启动、提交后、定时、请求触发的全量刷新共用实例内锁。等待其他刷新最多 300ms，每条目录 SQL 超时 2 秒，加载失败后冷却 1 秒；这些不是整个 HTTP 请求的硬时限。
- 已有快照时，后台检查失败保留旧数据，搜索和本地已命中的校验仍可用。需要查询或补齐缺失 ID 的操作遇到依赖错误返回 503。
- 非 Web 的索引维护命令不加载或调度标签目录。其他实例的新增可见延迟通常约一个检查周期，持续故障期间不承诺严格上限。

关注目录版本读取/加载/刷新失败日志及“文章标签不在完整目录中”错误。目录错误不能解释为合法的空搜索结果或文章不存在。

## 发布、核对与回滚

1. 备份文章与旧关系，停止旧应用及写流量。在专用同版本 MySQL 验证 V8/V9 后，执行迁移；不重写历史 V3。
2. 核对每篇文章 JSON 的数量和集合与旧关系相同，无标签为 `[]`，包括隐藏文章；迁移异常时保持停流量，不启动部分切换的应用。
3. 默认文章缓存格式升级为 v4，载荷只有 `tagIds`。已有环境显式覆盖 ARTICLE_CACHE_VERSION 时也必须改为未用过的新版本，不能复用 v3 或旧 DTO 前缀。
4. 参照[文章缓存恢复](article-crud-implementation.md)使用非 Web 命令从主库重建新命名空间的隐藏墓碑和完成标记，然后以相同缓存版本启动全部新实例。
5. 验证搜索、创建、编辑、详情、ES 同步与恢复后开放流量。保留旧表但不再读写；其数据从新写流量开始即可能陈旧。

恢复写入后不能直接回滚旧应用。必须停写，从当前 JSON 反向恢复旧关系并验证；文章缓存也需选择适合回滚模型的全新版本并重建墓碑。禁止清空共享 Redis。

## 验证入口与 SQL 口径

运行 `infra/test/run-search-tests.ps1 -Verify` 使用独立 MySQL 8.4、Redis、RabbitMQ 和 ES 环境。标签专项包含目录的真实 RR 视图、提交回滚、SQL 次数及随机专用数据库中的 V8→V9 迁移；测试库校验和随机命名空间沿用项目保护。

| 标签链路场景 | SQL 次数 |
|---|---:|
| 热搜索、空标签、已知 ID 校验 | 0 |
| 缺 ID 且版本一致 | 1 次版本读取 |
| 缺 ID 且需要加载 | 1 次版本读取 + 2 次完整快照读取 |
| 定时版本不变 | 每实例每周期 1 次 |
| 文章索引元数据批量读取 | 1 次，原为 2 次 |

原关系 DELETE/INSERT 已删除。认证、作者、媒体、计数及文章必要写入的 SQL 不包含在上述口径中。
