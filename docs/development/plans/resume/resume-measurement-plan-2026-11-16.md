## P0 实验要求

1. 固定 Git 提交及工作区状态，限定应用与依赖 CPU/内存；记录真实磁盘、MySQL 持久化参数、Redis 持久化、MQ 拓扑及客户端机器。旧项目的 2 核 2G 环境不能直接沿用为当前事实。
2. 仅用独立测试库、随机 Redis 前缀、独立 MQ vhost/索引；禁止全库 FLUSH 或修改生产实现。负载客户端独立，公开用户、文章数、正文长度、热点分布与缓存命中率。
3. 对照返回的 ID、用户点赞状态和计数必须相同。A/B 均纳入认证时保持一致；单测服务装配时明确不包含认证。基线和批量方案采用同等后台任务配置。
4. 固定负载速率与完整请求序列，先预热，再各测至少 300 秒，每组至少 10000 个有效样本，顺序用 A/B、B/A 交替，至少 3 轮。若负载过低导致样本不足应延长，而非插值。
5. 每轮记录计划/实际 RPS、成功率、状态码、异常、忙跳过/丢迭代、P50/P95/P99、SQL 调用次数、缓存命中、CPU/内存、连接等待。SQL 指标区分点赞子查询、卡片回源批次和 HTTP 总 SQL。
6. 缓存清理在请求计时外，清理只影响本轮 list key；这模拟强制卡片未命中，不冒充真实命中率。公共缓存与点赞缓存独立控制。热缓存测量持续时间超过 TTL 时须记录自然失效，不能一直称全热。
7. 预先约定判定：示例标准成功率≥99.9%、实际 RPS≥计划的 99%、P95<800ms/P99<1500ms；这是本次建议门槛，不是已有结果。记录全部重复结果，按每轮配对计算 `(A-B)/A`，报告中位数和范围，不挑最佳一轮。

### 历史方案细节（不作为当前执行指令）

以下保留首次方案的环境和限制；当前持久盘、产物目录与采样口径以统一性能文档为准。

脚本顺序复用 `run-like-tests.ps1 -Tests LikeCapacityTests -Load`，不启用破坏性故障选项；既有容量测试仍会短暂停止本轮应用消费者以测恢复。只连接 `easy-community-like-it` 专用资源，不与其他使用同一测试项目的任务并行。

脚本将每轮原始 JSON、日志、Surefire、Git 版本、工作区状态与本机资源保存到被忽略的 `backend/target/resume-like-<时间>-<随机ID>/`，默认不包含凭证或完整环境变量。之后执行 Maven clean 会删除 target，审核脱敏后及时复制到长期报告目录再运行 clean；不得覆盖旧报告。脚本检测本轮确有测试通过和新报告，不将门禁跳过算作测量完成。

**重要限制：现有 Compose 的 MySQL 使用 tmpfs。** 此入口只是当前版本同口径复测，不是生产持久盘验收，也不直接产生优化提升。持久盘实验需另建独立 Compose 项目、数据卷及端口并接入相同夹具，不应原地替换当前专用测试实例的数据目录。采集脚本不会修改基础 Compose。

现有容量测试仅有阶段末待提交值和全局最老年龄，不能据其证明阶段内持续稳定，也没有每条命令落库延迟分位数。长窗口正式容量验收前，另增时间序列采样（建议1秒）、消费完成速率、队列 ready/unacked、最老待提交年龄及 SQL 完成延迟；采样不应增加主库全表扫描。最终状态高版本覆盖低版本按状态收敛计，不宣称每次点击分别落库。

现有16个串行用户可能成为发压瓶颈：必须保留 skippedBusyClient，负载未达到计划时不报告为服务器容量。每阶段独立排空并预热后再比较，现有连续阶梯保留用于观察积压传播；两种实验应分别命名。
