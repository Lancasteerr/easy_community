# 压测结果汇总（2026-11-16）

结论：本机三轮观测中，推荐流约80 QPS正常完成；点赞60 QPS未见持续积压，120 QPS受理成功但消费落库跟不上；PV聚合显著减少写SQL，文章缓存减少回源但尾延迟收益不稳定。尚未测出生产容量上限。

## 环境与统计口径

- Windows 11、i7-14700HX、约15.78 GiB内存，Docker Desktop虚拟机约7.64 GiB；发压与服务同机，开发容器同时运行。
- MySQL 8.4、Redis 7.4、RabbitMQ 4、ES 9.5.6；MySQL使用持久卷，提交刷盘参数为1/1。容器分别限额2核/1.5 GiB、1核/256 MiB、2核/768 MiB、2核/1.5 GiB；测试JVM堆768 MiB，应用未限CPU，点赞双应用共享同一JVM。
- 常规阶段60秒、重复三轮；读取数据256篇文章、4作者、每页20篇；点赞16用户、32篇文章，测试提高入口限流。Core关闭推荐算分定时任务，PV保留60秒刷盘。
- 表中取三轮最低实际QPS、最高单轮P95/P99，延迟单位ms；成功数和发压丢弃为三轮合计。分位数不做平均，丢弃/忙跳过不计成功。

## 可能的性能限制及建议

以下原因结合数据与当前代码推断，尚未通过分段耗时或资源剖析全部定位。

| 现象 | 可能原因 | 建议 |
|---|---|---|
| 点赞120 QPS积压，热点更明显 | 每条消息独立事务，关系行加锁并更新同一文章计数行；热点阶段每轮记录3,898～4,044次MySQL行锁等待。持久卷提交成本也可能限制消费吞吐 | 优先采集事务耗时、具体锁等待及磁盘延迟；在60～120之间细化阶梯，按积压趋势控制入口。比较消费者数量，确认瓶颈后再评估按文章合并更新，保留版本幂等与精确计数语义 |
| 缓存减少SQL，P95却不稳定 | 小数据集下SQL批量读取已较快；Redis往返、解码及共享宿主调度可能抵消收益 | 保留减少回源的结论；分别测Redis/解码耗时、GC和SQL耗时，在更大数据量及独立发压环境复测 |
| 推荐流P99最高190.56ms，跨轮波动较大 | ES查询/PIT创建、缓存与装配串联，同机资源竞争也可能放大尾延迟 | 增加ES、缓存、装配分段计时，采集PIT数量及资源峰值，并补测连续翻页与冷缓存 |
| 索引观察延迟约秒级 | 当前Relay每轮结束后等待1秒、每批最多10条，轮询调度可能贡献明显等待 | 先测Outbox最老年龄、Relay及ES写入耗时；有时效需求时对照调整轮询间隔/批量大小，避免直接假定ES是瓶颈 |
| PV聚合收益明显但延迟降幅波动 | 请求内写入转移到周期刷盘，成本仍会在活跃文章增多时集中出现 | 监控刷盘耗时、待刷文章数与锁等待；扩展活跃文章数量及刷盘与编辑并发场景，再决定是否拆批 |

优先补齐全程CPU、GC、连接池等待、磁盘I/O及SQL锁监控；在目标部署环境使用独立发压机，每阶梯至少300秒、多轮复测，并验证长期积压与故障恢复。当前样本不足以确定容量上限或生产SLA。
