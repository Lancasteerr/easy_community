## 建议投递稿

**项目名称：** easy_community 多用户内容社区

**技术栈：** Java、Spring Boot、Spring Security、MyBatis-Plus、MySQL、Redis、Lua、RabbitMQ、Elasticsearch、React、TypeScript、MinIO、Docker

**项目简介：** 从个人博客演进的前后端分离内容社区，支持多用户与角色权限、富文本文章、图片管理、点赞、全文搜索及热度推荐。

**项目亮点：**

- **异步点赞与一致性：** 使用 RabbitMQ 确认发布与手动 ACK，结合 Redis Lua 版本签发、MySQL 关系状态与计数同事务更新，处理重复投递与乱序覆盖；历史本机双实例、MySQL tmpfs、30 秒均匀写实验达到约 **120 QPS**，受理接口 **P95 53.86ms**，实验结束 SQL 状态与计数对账一致。
- **可靠索引同步：** 将文章变更与 Outbox 事件同事务提交，通过租约领取、确认发布及 ES 版本条件更新处理提交后进程退出、重复消息和旧版本覆盖；配套死信重放、索引对账与别名切换，支持全文搜索和热度推荐。
- **批量查询与缓存：** 将点赞状态与计数按文章集合批量回源，50 篇文章的点赞数据最多使用 **2 条批量 SQL**；共享文章卡片与用户点赞状态分离，避免个性化状态进入公共缓存。**性能收益需补测：同负载下 P95【A→B ms】、每请求点赞 SQL【C→D 条】。**
- **媒体生命周期：** 使用 POST Policy 实现浏览器直传，按文件身份隔离私有临时区与公开区；将文章/头像引用更新纳入业务事务，通过引用保护、延迟回收和失败重试处理上传后未绑定及替换后的残留文件，完成 MinIO 真实服务集成验证。

投递前删除第三条的“性能收益需补测”句，或用完成对照实验后的真实数据替换。其余条目可以使用；第一条必须保留历史短测环境限定。篇幅紧张时保留点赞、索引、媒体三条，批量查询可并入点赞条目。

## 数据充分性结论

现有证据可以写“实现效果、历史容量观测、批量查询上界”，**没有可直接用于当前项目的可信优化前后提升百分比**。不能为了凑提升数字，把容量、恢复耗时、SQL 上界混成同一种指标。

优先补测“批量点赞查询对照”或“卡片缓存对照”，取得一条可信提升数据即可；不必为每项设计强行配数字。具体实验与采集入口见[补测计划](../../plans/resume/resume-measurement-plan-2026-11-16.md)。

## 面试需要能解释的设计取舍

- 点赞命令没有业务 Outbox，接受边界是已路由且 Broker Confirm；提交未知时返回未知，不能保证每次失败都未执行。Redis 签发器异常需停写、人工恢复纪元，运维成本较高。
- 每篇文章精确点赞计数仍竞争同一行；MQ 吸收峰值但不消除 SQL 热点，扩消费者不必然提升吞吐。单节点 Quorum 队列不构成节点容灾。
- 当前小规模系统引入 Redis、MQ、ES、对象存储，可靠性机制较完整，但部署及恢复复杂；应以搜索需求和可验证的最终一致性目标解释选型，不宣称微服务或大规模生产架构。
- ES 和公共卡片缓存存在可见性窗口，隐藏不承诺立即从所有查询消失；媒体超时不等于一定未提交，极端迟到复制可能留下对象。

以上限制不必全部塞进简历，但回答面试追问时应如实说明。
